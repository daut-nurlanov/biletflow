# BiletFlow final frontend audit

November 25, 2026. Audited on `feature/ui-redesign` at the current `origin/main` base `213e09d`, with the frontend redesign still in the working tree.

Sources are the original [SRS v0.3](BiletFlow_SRS_Initial_Draft.pdf), [README](../README.md), [team assignments and scope clarification](TASKS.md), [demo script](DEMO_SCRIPT.md), [architecture decisions](ARCHITECTURE_DECISIONS.md), and the implementation. SRS §8 and §13.4 put assigned seating and calendar export in the bonus scope. TASKS §1 records the instructor clarification that one mobile app must serve attendees, organizers and door staff, with the website carrying workflows that do not require native parity. The SRS describes sandbox or simulated financial workflows for the MVP. This audit used the isolated QA API and database with outgoing SMTP disabled.

## Confirmed fixes

- The web homepage banner is text-only and fits its content. Catalogue card artwork and organizer-uploaded event photos remain available.
- Web detail pages now give a reason and disable ticket choices for draft previews, unavailable events, registration restrictions and closed ticket windows.
- The two ticket wallets show historical events separately from server ticket status. The web wallet refreshes when the tab regains focus. Refunded and used tickets retain their status even when the event later becomes cancelled or suspended.
- The current scanner contract permits admission for an unused ticket from a completed event. Both wallets identify the event as past and preserve the server-defined ticket state and QR. A hard post-event admission cutoff needs an explicit policy and a shared backend enforcement rule.
- Web refund and cancellation actions lock after an uncertain response until the operator refreshes status. Confirmations now precede suspending users or events and freezing paid sales in the administrator portal.
- Browser regressions check draft and closed ticket selection, past-event labels, refund recovery, and the existing QR status rules. The live integration fixture uses a valid phone format for the current profile validator.
- Registration uses persistent field labels, standard autofill and the same 72-byte password limit as reset and Android. Multiple tickets for the same event have distinct accessible open-ticket labels.

## Test environments and artifacts

- Chrome uses the repository CDP browser harness and isolated Docker API at port 8004. Rendered captures use 1440 × 900, 1024 × 768, 768 × 1024, and 390 × 844. The layout report includes page and viewport widths and language.
- None of 39 captured views showed page-level horizontal overflow. The homepage banner was text-only at all captured widths. Axe-core 4.14.1 reported zero WCAG-tagged violations in nine sampled states, including the English catalogue and detail, Russian phone catalogue and Kazakh phone wallet. This is a sample of rendered states and leaves keyboard coverage, production conformance, and screen-reader testing open.
- Android testing uses `BiletFlow_API35`, Pixel 7 class Android emulator, with Expo SDK 58 and agent-device. Staff camera tests use the emulator virtual camera and QR images generated for isolated QA tickets.
- Screenshots, downloaded PDFs and detailed visual reports are under Git-ignored `mobile/.expo/final-qa/`. Do not include test account data, QR images or build output in source control.

The final browser regression run passed 75 checks, with the live workflow run separately and passed. The mobile suite passed 68 checks, including both live suites. Web production build and ESLint, mobile TypeScript and ESLint, Expo dependency compatibility, Expo Doctor (20/20), and Git whitespace checks passed.
