## Implementation and fixes

| Severity | Finding | Change and verification |
| --- | --- | --- |
| P0 | A native paid purchase stayed on Confirming after successful quote preflight. API logs showed no checkout request. The asynchronous crypto import was between the successful preflight and storing the attempt. | Kept crypto evaluation deferred until checkout, with a synchronous literal Metro require inside the existing guard. This removes the dev chunk wait. The missing-module test still rejects before storing/submitting. Native paid and free purchases succeeded after a cold launch. The development hang diagnosis is based on this execution path and the before/after result. [Metro module behavior](https://metrobundler.dev/docs/module-api/) |

Details and dashboard derive the same date-aware phase for their full event records and retain explicit draft, cancelled and suspended states. The emulator list displayed Completed after the fix. |

| P2 | Multiple ticket types had identical accessibility actions. Manual search results for two tickets of the same type and attendee also had indistinguishable undo actions. | Give the type-choice actions specific labels. Show the ticket ID suffix on the attendee card and staff result, and include it in named staff actions and the undo confirmation. Verified manual check-in and undo on the same referenced ticket. |

New screens use the existing authenticated API client and resource hook. Purchase history reads `/api/orders/my-orders` and links each order to support. Event activity reads the event-scoped timeline. Door staff uses the event-scoped list, assign-only and revoke routes. Assignment input is validated, concurrent taps are locked, removal asks for confirmation, and the list refreshes after the request. Backend authorization remains the authority for all three screens.

## Limits and acceptance work

- **Intentional web workflows.** Organizer identity and payout setup, editing events and ticket types, publishing and activating paid sales, creating campaigns, new staff account creation, refunds, full audit filters and the advanced support desk remain on web. The platform admin portal remains on web.
- **Deferred and backend limitations.** Seat inventory and holds exist. The optional seat-picker UI needs coordinated hold expiry, conflict and checkout recovery UX. Admission requires server connectivity. Email delivery, production payments and payout execution, and partial refunds are outside this demo.
- **Remaining native acceptance.** Physical iOS checks below remain open. One portrait Android size and normal font scale were exercised. External PDF viewing, denied-permanently system settings, larger font scales and lower-memory devices did not receive a separate run. The automated suite covers suspended-event admission and QR visibility combinations. Timing races and lost checkout responses were tested with the regression harness rather than repeated live device faults.

## Repeatable final demo

1. Bring up the existing Docker Compose backend and database. When updating backend code, use `docker compose up -d --build` so migrations run while preserving the volume. For disposable rehearsals, reuse an isolated QA database and API. This run used host port 8004 and the same backend image with the workspace source mounted.
2. Start the existing Android AVD. From `mobile`, dot-source `.expo/device-qa/Use-AndroidQa.ps1`, set the process variable `EXPO_PUBLIC_API_URL` to `http://10.0.2.2:8004` for the QA API, and run `npx expo start --port 8084 --localhost`. Reverse port 8084 with `adb -s emulator-5554 reverse tcp:8084 tcp:8084`. Open the installed debug app using `agent-device open com.biletflow.mobile --platform android --serial emulator-5554 --session biletflow-visual --metro-host 127.0.0.1 --metro-port 8084 --no-test-ime`.
3. On the website, sign in as an organizer with a verified demo profile. Create a public event with future Almaty start/end times and capacity 20. Add 10 General tickets at 5,000 KZT each and 10 free tickets. Publish, activate paid sales using the simulated terms flow, and create a new event-scoped 20% campaign. [Setup and demo accounts](SETUP.md)
4. On mobile, open that event's dashboard as organizer and assign an existing staff account. Sign out. Register a disposable attendee and open the event in Events. Show the date, venue and ticket types. Pick two General tickets. Try an invalid code, remove it, then use the campaign so that 10,000 KZT becomes 8,000 KZT. Buy with simulated payment.
5. Show the receipt, QR and Purchase history. Go back to the receipt using Events. Use Get help with this order to create a request. Repeat purchase with a free ticket if demonstrating both price paths.
6. Sign in as assigned staff and scan the paid QR. Show the green admission and the red duplicate refusal. On the emulator, start with `-camera-back virtualscene`, load a disposable ticket PNG with `adb -s emulator-5554 emu virtualscene-image wall <png>` and `adb -s emulator-5554 emu virtualscene-image table <png>`, then play `Walk_to_image_room` from the emulator's `resources/macros` directory. Open Attendees, search for the buyer email, and demonstrate check-in and undo on a separate ticket reference.
7. Return as attendee, refresh My Tickets and show the checked-in ticket without an admission QR. Open the dashboard as organizer and show the matching attendance and event activity. Reply to the order request, then return as the attendee to show the reply. For a platform administration demo, use the separate web portal.

Use the app and web against the same API. If a seeded promo event has passed its sale window, use a future disposable event with a new campaign. Leave the original database and demo records in place.
